Claude Code のチームは、AI が書くコードをどうレビューしているか

元の記事Addy Osmani、Morgan Westlee Lunt、Qing Wang「How the Claude Code team does code review」claude.dev Blog（Engineering）、2026-10-15。Anthropic の Claude Code のチームが、自分たちのやり方を書いた記事です。査読のある論文ではありません。記事のページには、ライセンスの表示がありません。 元の記事（claude.dev）

Claude Code のコードは、約 9 割を Claude が書いています。人が 1 行ずつ読むレビューでは追いつかない量です。この記事は、Claude Code のチームがレビューをやめずに、読む仕事の大半を機械に移し、人の承認をリスクのある変更に絞ったやり方を書いています。

2026-11-18 に下書きを作成（microtaro と AI）。数字と事実は、同日に元の記事と照らし合わせました。記事が言っていることを、この解説で立てた問いの順に並べ直しています。記事の節の順ではありません。

新しい研究の論文ではなく、1 つのチームが自分たちのやり方を書いた記事です。記事から読み取れる問いを 5 つにまとめます。灰色の小さな字は、記事のどの節から読み取ったかです（節の名前は原文のまま）。

Q1

Claude Code のチームは、レビューで何を目指し、何で測っているか。

A

差し戻しと障害を増やさずに、人がレビューに使う時間を減らすこと。ほとんどの PR（変更を取り込んでもらう申し出）を、人が最大 1 人（書いた本人でもよい）関わるだけでマージできるようにする。

答えのもとになった記事の内容

  • 人の時間は 2 つある。レビューにかける時間と、悪い変更が壊したものを直す時間。前の時間を減らしても後の時間が増えれば、人の時間を別の所へ移しただけになる。だから、差し戻しと障害の率を歯止めにする。記事の「The scarce resource: human time and attention」から
  • 問いを変えた。「人がコードを読んだか」ではなく、「この変更で何がまずくなりうるか。それを捕まえるのに向いた確かめは、自動か、人か」を問う。記事の「Rethinking the purpose of code review」から

Q2

1 つの変更は、マージされて利用者に届くまでに、どんな確かめを通るか。

A

関門を 1 つにせず、確かめを層に重ねる。PR を出す前に Claude が自分の作業を確かめ、PR ごとに必須の CI、AI のレビュー、セキュリティのレビュー、リスクに応じた人の承認を通る。マージのあとも、フラグと少しずつの公開で、すぐ戻せるようにしておく。

Q3

人の承認は、いつ、何人要るか。

A

変更のリスクで決める。リスクが低ければ 0 人（自動の確かめが通れば）、ふつうの変更は 1 人、いちばん危ない所は 2 人。段階は書いた人ではなく変更の中身で決め、AI の承認は人の承認に数えない。

答えのもとになった記事の内容

  • 段階は、分類器が変更を読んで決める。もう 1 つの分類器が、段階によらず人が要る変更かどうかも見る。持ち主が敏感だと指定したパスと、CI のワークフローのファイルは、いつも人が要る。記事の「Layer by layer」の 5 から
  • 承認は、特定の commit に対するもの。エージェントの push や、人が手で解いたマージのように、仕組みが中身を保証できない commit があとから入ると、承認し直しになる。記事の「Layer by layer」の 5 から

Q4

AI が書き、AI がレビューすると、往復が終わらなくなることがある。どう対処したか。

A

3 往復したら、やり方を考え直すよう書き手に求める上限を入れ、何回か往復したあとは新しい差分だけを見直すようにした。社内の PR で、1 回の直しで通る割合が 65% から 78% に増えた。

答えのもとになった記事の内容

  • 50 往復を超えた PR があった。ある CLI の PR が、一晩でレビューと直しを 50 回を超えて往復し、書いた人が止めた。何度も指摘された所の約 59% は、最初のレビューの時点からあったコードだった。記事の「How we make the reviewer better」から
  • 書き手がエージェントだと、細かい指摘が高くつく。人なら数秒で流せる細かい指摘も、エージェントは直してしまう。そのぶん commit が増え、レビューがもう 1 往復増える。記事の「How we make the reviewer better」から

Q5

機械が読む仕事の大半を引き受けたあと、人に残るのは何か。

A

作るかどうかを決めること、危ないコードと人がまねる設計をレビューすること、確かめの証拠を読むこと、出した変更に責任を持つこと。

答えのもとになった記事の内容

著者が言いたいこと

著者の結論（記事の冒頭と、最後の節「Where this is going」）

レビューをやめたのではない。読む仕事の大半を機械に移し、人の時間と注意はリスクのある所に使い、間違いはすぐ見つけて戻せるようにした。目標は変わらず、変更 1 つあたりの人の時間を減らし、差し戻しは今より増やさないこと。

だから著者は、自分のチームで取り入れるときに、次のことを勧めています

  • PR の前：エージェントが自分で走らせられる確かめを渡す。確かめ方を短い CLAUDE.md に書き、整形と lint は hooks で走らせる。手元でもレビューを走らせる。くり返し書くレビューのコメントは、REVIEW.md に移す。
  • PR ごと：マージを止められる確かめを重ねる。CI を必須にし、AI のレビューと自動のセキュリティのレビューを入れ、すべての指摘を片付けてからマージする。レビューの手間はリスクに合わせ、往復には上限を付ける。AI のレビュー役は 1 つのリポジトリで始め、数週間 REVIEW.md を調整してから広げる。
  • 承認：リスクの段階を書き出す。段階は変更で決め、厳しく始めて、証拠を見ながら緩める。認証、課金、CI とリリースのワークフロー、インストーラーには、いつも人が要るようにする。bot の承認で人の承認を置き換えず、新しい commit が入ったら承認を外す。
  • マージのあと：すぐ戻せるようにして、測る。マージキュー、フラグ、まず社内で使うこと、少しずつの公開、1 回の操作で戻せること。障害と差し戻しを評価の問題集にして、レビュー役を変えるたびに採点し直す。人の時間を測り、差し戻しと障害の率を歯止めにする。

記事の「How you can adopt this process」の一覧を、4 つにまとめ直したものです。詳しくは 9。

記事が答えていないこと

著者自身が、まだできていない、まだ決まっていないと書いていること：

  • 自動で厳しくする仕組み：差し戻しや障害の数字が動いたときに、承認を自動で厳しくする仕組み（circuit breaker）は、まだない。
  • 悪いマージに気づくこと：いまも、書いた人、当番、ダッシュボードに頼っている。
  • 人なしでマージしてよい範囲：どの低リスクの変更を自動の確かめだけでマージしてよいかは、持ち主が決めていて、その線はまだ動いている。

3何を目指し、何で測っているか（Q1）

目指すのは、ほとんどの PR を、人が最大 1 人関わるだけでマージすることです。人の時間を減らせたかどうかは、差し戻しと障害の率が上がっていないかで確かめます。

  • きっかけは変更の量：Anthropic の monorepo（会社の多くのコードを 1 か所にまとめたリポジトリ）では、1 日に入る変更が、5 月の約 2,500 から 9 月の 30,000 以上になった。Claude Code のリポジトリは別だが、同じように増えている。
  • 対象：Claude Code のリポジトリ。CLI、デスクトップと Web のアプリ、モバイルのアプリが入っている。
  • 測るもの：PR あたりの人の承認の数（中央値と、95 パーセンタイル）、人のコメント、PR が人を待つ時間。
  • 歯止め：差し戻し（revert。入れた変更を取り消すこと）の率と、障害（incident）の率。レビューの時間が減っても、壊れたものを直す時間が増えれば、人の時間を移しただけになるから。

41 つの変更が通る確かめの層（Q2）

どの層にも、捕まえる問題と通してしまう問題があります。層を重ねて、全部を通り抜ける問題を減らし、それでも通ったものは、すぐ見つけて戻します。人が関わるのは、リスクに応じた承認の層だけです。

PR ごと必須の CIlint、型、全プラットフォームでのテスト、ビルド。通らなければマージできない自動
AI のレビュー複数のエージェントがバグを探し、別のエージェントたちの投票で絞った指摘を出す自動
セキュリティのレビュー別の自動のレビュー。開いたままの指摘があるとマージできない自動

マージするときマージキュー最新の main に変更を当てた状態で、確かめをやり直す。別々なら通る 2 つの PR が、合わさって main を壊すのを防ぐ自動

AI のレビューの中身

  • 何を見るか：差分を、リポジトリ全体と PR に書かれた意図に照らして読む。
  • 指摘の絞り方：複数のエージェントが並行してバグを探し、別のエージェントたちが指摘ごとに投票する。十分な票を得た指摘だけを出す。書き方、診断、片付けだけの指摘は落とす。この絞り込みは、自分たちの PR で A/B テストしてから入れた。
  • 指摘の札：指摘には、Important、Nit、Pre-existing のどれかが付く。Pre-existing は、その PR が入れたのではないバグで、書いた人のせいに見えないようにするための札。
  • 指摘への応じ方：直すか、理由を書いて閉じる。開いたままだとマージできない。
  • 深さ：管理者が、リポジトリごとに Quick、Standard、Deep から選ぶ。
  • 既にあるコードも：レビューのエージェントは、毎晩、既にあるコードも見て回る。

AI のレビューの研究プレビューを始めたとき、中身のある指摘が付く社内の PR は 16% から 54% に増えました。1,000 行を超える PR にはたいてい指摘が出て、小さい PR にはたいてい何も出ません。公開されている製品は Code Review for Claude Code（Team と Enterprise のプラン）で、/code-review は、その軽い版を手元で走らせます。

5人の承認は、変更のリスクで決める（Q3）

文書の直しと、自動更新の仕組みの変更では、危なさが違います。だから人の承認の数を、変更のリスクの段階で変えます。段階を決めるのは書いた人ではなく、変更の中身です。

段階どんな変更か人の承認
低い文書、文言、社内だけの機能、フラグの裏に足すだけの変更要らない（自動のレビューとセキュリティの確かめが通れば）
ふつうふつうの製品の変更。キャッシュ、自動更新、システムプロンプトのような敏感な所の変更も1 人
高いいちばん危ないコード。いつも 2 人が要る少数のパス2 人

記事の「Layer by layer」の 5 の表を、microtaro と AI の言葉で言い直したものです。

  • 段階は分類器が決める：変更を読んで段階を選ぶ分類器と、段階によらず人が要るかどうかを判断する分類器がある。持ち主が敏感だと指定したパスと、CI のワークフローのファイルは、いつも人が要る。
  • 軽い道は、信頼された書き手だけ：リポジトリの信頼された書き手（主に、そのコードを持つチーム）でなければ、2 人目の承認が要る。
  • AI の承認は数えない：エージェントの承認は、人の承認として数えない。自動のレビューは低リスクの変更を通せるが、人が要る枠は埋められない。
  • 指示した人が責任を持つ：エージェントが書いた PR では、エージェントに指示した人が、必要な承認者の 1 人に数えられる。
  • 承認は commit ごと：承認は特定の commit に対するもの。仕組みが保証できない新しい commit（エージェントの push、人が手で解いたマージ）が入ったら、承認し直しになる。

6AI のレビュー役を良くし、往復を終わらせる（Q4）

レビュー役は、過去の障害から作った問題集で毎日試し、役に立たない指摘の多さも測っています。AI どうしの往復が終わらなくなる問題には、往復の上限などを入れ、1 回の直しで通る PR が増えました。

レビュー役の良さを、どう測るか

  • 障害を問題集にする：過去に障害や差し戻しを起こした PR を、その後の直しと一緒に集め、そのコードを知るエンジニアが、バグとその場所を 1 つずつ確かめた。この問題集（eval）で、レビュー役を毎日試す。
  • 役に立たない指摘も測る：バグでないものも大量に出してよいなら、バグを多く捕まえるのは簡単。だから、人が指摘にどう応じたか（直した、間違いだと言った、わざとだと言った、問題にならなかった）で分ける。問題がないと分かっている PR にもレビュー役をかけ、有害な直しにつながりかねない報告の数を数える。
  • 優先の順：1 番目は本物のバグを捕まえること、2 番目はレビューの往復を減らすこと。

往復が終わらなくなる問題

  • 起きたこと：ある CLI の PR が、一晩でレビューと直しを 50 回を超えて往復し、書いた人が止めた。
  • 調べて分かったこと：何度も指摘された所に git blame（その行をいつ誰が書いたかを調べる命令）をかけると、約 59% は、最初のレビューのときからあったコードだった。その PR の新しいバグではなく、もとからあったバグを、毎回少しずつ見つけていた。
  • 入れた変更：3 往復したら、レビュー役が書き手に、一歩引いてやり方を考え直すよう求める。何回か往復したあとは、新しい差分だけを見直す。1 か所ではなく、バグの種類を指摘して、同じ種類の所を全部直させる。一度出した指摘はくり返さない。
  • 追う数字：通るまでの往復の数を、見逃しの少なさ（recall、本物のバグのうち捕まえた割合）と並べて追う。

レビュー役に渡す指示：CLAUDE.md と REVIEW.md

  • CLAUDE.md：プロジェクトが何か（使っている技術、決まり、目標、やらないこと）を書く。レビューのたびに読み込まれるので短くし、詳しいことはほかの文書を指す。レビュー役は、ここの決まりを破るコードや、ここの記述を古くする変更も指摘する。
  • REVIEW.md：コードの持ち主が、自分の持ち場で何が大事かを、レビュー役に伝える。記事が良いとする REVIEW.md は、短く、そのリポジトリでの「失敗」を定義する。例は、文書なら嘘を書くこと、設定なら行き先を間違えること。細かい指摘（nit）の数に上限を付け、見なくてよいパスを挙げ、名前からの推測ではなく、ファイルと行を根拠として求める。まとめは件数から始め、直すものがないときはそうはっきり書かせる。
  • くり返しは、もとを直す：同じ指摘が何度も出るなら、skill、lint の規則、指示のファイルのどれかを直す。レビューが何かを見逃したら、モデルの前に何がなかったかを問い、直しを CLAUDE.md、skill、新しい確かめに入れる。

7機械が読むようになっても、人に残る仕事（Q5）

人に残るのは、判断と責任です。作るかどうかを決め、危ない所と人がまねる設計を見て、確かめの証拠を読み、出した変更に責任を持ちます。

  • 作るかどうかを決める：方向、好み、範囲。
  • 危ないコードをレビューする：課金、自動更新、CI のワークフローなど。
  • 人がまねる設計をレビューする：ほかの人が型として写す設計。
  • 証拠を読む：テストの出力、走らせたコマンドと結果、スクリーンショット、レビュー役の指摘。確かめが何を見逃しうるかを言えないなら、さっと承認せず、ちゃんとしたレビューを頼む。
  • 結果に責任を持つ：誰が打ったかによらず、出ていく変更のすべてに、責任を持つ人がいる。

入れた人が直す

小さい変更や中くらいの変更を入れて何かがまずくなったら、たいてい入れた本人が直す、というのがチームの決まりです（記事の言い方では “You land it, you own it”）。責めるためではなく、直す本人がいちばん事情を知っているからです。記事は、これが回る理由を 4 つ挙げています。

  • 変更が小さいので、レビューも、原因探しも、差し戻しもしやすい。
  • フラグ、差し戻し、少しずつの公開で、たいていの間違いを戻せる。
  • 影響の広さで基準を決める。影響の大きいコードほど、人も確かめも多くする。
  • 後退（以前は動いていたものが動かなくなること）が、テレメトリ（使われ方や不具合を送る仕組み）と社内での利用で、すぐ表に出る。

コードの理解をどう分け合うか

  • レビューには、問題を見つけるほかに、チームでコードの理解を分け合う役目もあった。機械が読む仕事の大半を引き受けると、その役目をどうするかが残る。
  • 正式な仕組みはない。チームの誰も Claude Code の全体を頭に入れておらず、誰もそれが必要だとは考えていない。
  • ある部分を知りたいときは、その部分の解説を Claude に書かせる。図にした小さなページを作らせる人もいる。誰でも見られる Slack のチャンネルで働くので、ほかの人が作っているものを、作っている最中に見られる。

方向を変えるとき

エージェントのおかげで作業を始めるのが安いので、始めるべきでなかった作業も出てきます。たいていは、チャンネルの誰かが理由を聞いたり、前の決定を示したり、もっと簡単な道を出したりして、書いた人が PR を閉じるか作り直します。コードをすぐ書けたので、PR を閉じても損をした気にならない、と記事は書いています。勧めているのは、別の方向を、できあがった PR を止めるコメントとしてではなく、早いうちにスレッドで出すことです。

  • 書いた人：Anthropic の 3 人（Addy Osmani、Morgan Westlee Lunt、Qing Wang）。
  • 対象：Claude Code のリポジトリ（CLI、デスクトップと Web のアプリ、モバイルのアプリ）。一部の数字は「社内の PR」とだけ書かれ、どのリポジトリのものかは分からない（2）。

9著者の勧めと、記事が認めている限界

勧めは、1 の「著者が言いたいこと」の 4 つです。記事は、この進め方の部品のほとんどは、いま手に入るものだとしています。

限界中身
自動で厳しくする仕組みがない差し戻しや障害の数字が動いても、承認は自動では厳しくならない。人なしのマージを広げる前に、エンジニアたちはこの仕組みを欲しがっている
悪いマージに気づくのは人頼み書いた人、当番、差し戻しと障害のダッシュボードに頼っている
人なしでマージする範囲は動いているどの低リスクの変更を自動の確かめだけでマージしてよいかは、持ち主が決めていて、まだ動いている
数字は 1 つのチームの社内のもの比べ方の詳しいことや PR の件数は書かれておらず、ほかのチームにそのまま当てはまるかは分からない（2）

上の 3 つは、記事自身が書いている限界です。いちばん下は、記事の数字の書き方から、microtaro と AI がまとめたものです。
