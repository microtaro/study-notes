1. 命令型UIと宣言型UI

画面に「こんにちは」を表示する

同じ一文を、逆の向きから見る

図で見る

命令型UI

プログラム変数 messageこんにちは
命じる
画面こんにちは

「画面に message を表示しろ」

プログラムが自分で画面を書き換える。実行が見えている

宣言型UI

プログラム状態 messageこんにちは
見る
画面こんにちは

「ここには message を表示する」

「今の状態なら何を見せるか」だけを書く。誰が画面を書き換えるかは隠れている

コードで見る（C++ と React の仮想コード）

色の行は、画面を書き換える実行

命令型UI（C++）：変えるたびに画面へ命じる

// 最初（message はただの変数）
std::string message = "こんにちは";
screen.show(message);

// 「さようなら」に変えるとき
// もう一度、画面に命じる
message = "さようなら";
screen.show(message);

宣言型UI（React）：状態を変えるだけ

// 最初（message は状態。React が見ている）
const [message, setMessage] = useState("こんにちは");
return <Screen>{message}</Screen>;

// 「さようなら」に変えるとき
// 状態だけを変える
setMessage("さようなら");

React が担う表示更新（説明用の仮想コード）

screen.show(message);

どちらも命令の形。違うのは相手

screen.show(message)　→　画面に命じる

setMessage("さようなら")　→　状態に命じる

画面を書き換える実行は、どちらにもある。自分のコードにあるか、React の中にあるかが違う。C++ でも宣言型で書く仕組みはある。分かれ目は言語ではなく書き方。

2. 宣言型のよさと「購読と通知」

部品が増えたときに何が楽になるか。そして、画面が状態を「見る」裏側の仕組み

宣言型にすると、画面の食い違いが減る

例：メッセージを送っている間は「送信」ボタンを押せなくし、「送信中…」を出す

命令型

部品ごとに命じ、終わったら部品ごとに戻す。戻し忘れが起きやすい

押せなくしろ、送信中を出せ
→ 押せるようにしろ、送信中を消せ

宣言型

「送信中だけ押せない・見える」と書いておき、状態を変えるだけ

送信中 → 待機中

同じ理由で、計算で出せるものは状態にしない。「入力が空のときは送信ボタンを押せない」なら、持つのは入力中の文字（message）だけ。押せるかどうかは、そこから計算する。

裏側では「購読と通知」が動いている

宣言型では、プログラムは画面に命じない。だから、変わったら教えてもらう仕組みが要る

① 購読＝通知の受け取り先として登録（最初に 1 回）

プログラム状態 message
購読
画面

「message が変わったら教えて」

② 通知（変わるたびに）

プログラム状態 message
通知
画面

「message が変わった」

通知が伝えるのは「変わった」だけ。何を描くかは画面の記述が決める

だから、ふつうの変数を変えても画面は変わらない

// ふつうの変数：誰にも知らせない。画面は変わらない
let message = "こんにちは";
message = "さようなら";

// useState：setMessage で React に次の描画を依頼する
const [message, setMessage] = useState("こんにちは");
setMessage("さようなら");

この通知は、オブジェクト指向の Observer パターンにたとえられる。React の useState では、更新関数が次の描画を依頼する。ただし setMessage の直後は、message はまだ前の値。新しい値は、次に作り直したときから使える。

講義資料の出典（原版での確認日 2026-11-23）

  • React 公式：Reacting to Input with State（命令型と宣言型の比較）、Choosing the State Structure（計算で出せる値は状態にしない）、State as a Snapshot（新しい値は次の描画から）
  • React 公式：State: A Component's Memory（ふつうの変数を変えても描き直されない）、useSyncExternalStore（subscribe で購読し、変わったら知らせる）

3. WPF と React の違い

React は、状態から画面の記述を計算し直す

WPF（Windows の画面を作る仕組み）では、画面の部品はオブジェクトで、ずっとそこにある。React では、状態が変わると部品の関数を呼び直し、前回と違う所を画面に反映する

違い①：部品が居続けるか、毎回作り直すか

例の画面：入力欄に「さようなら」と打つと、表示欄も「さようなら」に変わる

書き換わる所作り直した所

オブジェクトの流儀（WPF）

オブジェクトプロパティ Messageさようなら
つなぐ
画面入力欄さようなら

「ここは Message とつなぐ」

つないだ所だけ書き換える

React の流儀

部品状態 messageさようなら
作り直す
画面入力欄さようなら

「ここには message を表示する」

まるごと作り直し、前と違う所だけ書き換える

作り直すので、部品の中に置いたふつうの変数は、毎回消える。残したい値は、React に預ける（状態）。

違い②：React では、どの部品に預けるかが設計になる

画面は、部品の中に部品が入った入れ子。入力欄と表示欄の両方が message を使う

この WPF の例では、値をバインド先のオブジェクトに置いた。React では、どこに預けるかを決める

だから React では、状態管理を意識しないといけない

WPF では、つなぐ（バインディング）と、値が変わったと知らせる処理を、自分で書く。React では、値を変える関数（setMessage）を呼ぶだけ。WPF は Windows の UI、React はこの例では Web の UI に使っている。

講義資料の出典（原版での確認日 2026-11-24）

  • Microsoft Learn：Data binding overview (WPF .NET)（バインディングは画面の側を値の側につなぐ。値の側は INotifyPropertyChanged などで変化を知らせる）
  • React 公式：Render and Commit（違いがあるときだけ画面を変える）
  • React 公式：State: A Component's Memory（部品の中のふつうの変数は、作り直すと残らない）
  • React 公式：Sharing State Between Components（2 つの部品で使う値は、共通の外側の部品に置き、値と変える関数を渡す）

4. なぜ状態管理が要るのか

3 の ○ の図で決めていたのは、3 つのこと。これを決めるのが状態管理

状態管理で決める 3 つ

3 の ○ の図（2 つを包む外側に預けた）

  1. ① どこに置くか：本物は 1 か所だけにする（React 公式は single source of truth と呼ぶ）
  2. ② 誰が変えてよいか：変える入口を絞る。ここでは渡した関数 1 つ
  3. ③ 誰に伝えるか：使う部品に届ける（2 の購読と通知）

画面の中での置き場所は、狭い順に、共通の外側の部品、Context（間の部品を飛ばして渡す React の仕組み）、ストア（次の 5 で見る）。

実際にあった例

microtaro が AI と作ったアプリで、同期の結果を 4 か所（サーバーのメモリ、ファイル、ブラウザ内の保存、画面のキャッシュ）に持っていた。古い表示が残り続け、直すのに 1 日で 11 回の修正が要った。

置き場所は、値の種類（部品の中、画面全体、サーバーにあるデータの写し、URL など）で変わる。第7節の配置図で、種類ごとの例を見る。

講義資料の出典（原版での確認日 2026-11-23）

  • React 公式：Sharing State Between Components（共通の親に移す、single source of truth）、Passing Data Deeply with Context（間の部品を飛ばして渡す）

5. Zustand：部品の外に置く共有の箱

使う部品だけが、直接つなぐ

離れた部品が同じ値を使うなら、部品の入れ子の外に箱（ストア）を置く。Zustand は、その箱を作る定番の道具

React の流儀：未読の件数をどこに置くか

例：未読の件数。バッジはヘッダーの中、既読ボタンは一覧の中にある

画面全体に預ける（3 の形）

使わない部品も、受け取って渡す。件数が変わると、画面全体が作り直される

ストアに置く（Zustand）

使う部品だけが、直接つなぐ。件数が変わると、件数を使う部品だけが作り直される

サーバーのデータの写し（一覧の中身など）は、ストアに入れない。取り直しを全部自分で書くことになる。写しは TanStack Query に任せる（7）。

AI が書くコードでは、create(...) で箱を作り、useUnreadStore((s) => s.count) のように、使う値を選んで取り出す形で出てくる。

講義資料の出典（原版での確認日 2026-11-25）

  • Zustand：pmndrs/zustand（Provider なしでどこからでも使える。選んだ値が変わったときだけ作り直す）
  • React 公式：memo（外の部品が作り直されると、中の部品もふつうは作り直される）
  • TanStack Query：Does TanStack Query replace global state managers?（サーバーのデータは Query に任せ、ストアには画面の値だけを置く）

6. HTTP サーバーと「ステートレス」

HTTP のリクエストは、1 回ずつ意味が通る

画面（ブラウザ）は、開いている間ずっと動き続ける。HTTP では、サーバーは個々のお願い（リクエスト）の意味を、前のリクエストと切り離して解釈できる。ログインの続きは、例えばクッキーが示すセッションを読み出して扱う

動き方の違い

サーバーのメモリに、利用者ごとの続きを置かない。誰かはクッキーで確かめ、本物は DB から読む

こうしておくと、サーバーを再起動しても、台数を増やしても、どのお願いにも同じように答えられる。

「ステートレス」は、状態がないという意味ではない

画面の状態（1〜5）

ブラウザのメモリにある値。画面を開いている間、残る

ステートレス（HTTP）

サーバーが、前のお願いを覚えていなくても答えられる、という HTTP の決まり

講義資料の出典（原版での確認日 2026-11-25）

  • IETF：RFC 9110 HTTP Semantics（HTTP はステートレス）
  • IETF：RFC 6265 HTTP State Management Mechanism（クッキーで、続きのあるやり取りを保つ）
  • MDN：An overview of HTTP（ステートレスだが、セッションがないわけではない）

7. フロントとバックをどう分けるか

分けるのは、理由があるときだけ。理由がなければ、ブラウザだけで作る

状態管理から見ると

4 の「決める 3 つ」は、フロントとバックをまたぐと答えが変わる

決めること画面の中（2〜5）フロントとバックをまたぐと
どこに置くか共有の場所に 1 つ皆で使う状態の本物はサーバー（DB）。ブラウザにあるのは写し
誰が変えてよいか変える入口を絞るサーバーが認めた変更だけ。承認・確定のような移り変わりは、サーバーが守る
誰に伝えるかReact が自動で通知する自動では届かない。画面が取り直すか、サーバーから知らせる（ポーリング、SSE、WebSocket）

フロントとバックの境目は、状態の本物と写しの境目でもある

ブラウザの状態は、利用者ごと・タブごとに別々。他の人がサーバーで変えた内容は、取り直すまで画面に出ない。2 人が同時に直したときの上書きは、保存するときに版を確かめて防ぐ。

どこに何を置くか

ブラウザ

画面を見せ、操作を受け取る

状態と保存

  • その場かぎりの状態useState再読み込みで消える
  • 画面をまたぐ状態Zustand再読み込みで消える
  • サーバーのデータの写しTanStack Query古くなることがある
  • ブラウザ内の保存localStorageその端末だけに残る

処理

  • すぐ反応する処理
  • 入力中のチェック
  • 重い計算Web Workers・WebAssembly

画面の道具：React、Vite

サーバー

頼まれて処理し、返す

処理

  • 任せられない判断誰のデータか、払ったか
  • 保存するときのチェック
  • 秘密を使う処理
  • 閉じても続ける処理
  • 入口が複数の決まり画面・CLI・MCP から使う

道具：FastAPI（Python）、Hono・Express（JavaScript）

DB

データを残す

データ

  • 皆で使うデータの本物残る。別の端末や他の人からも見える

道具：PostgreSQL、SQLite

Next.js　画面とサーバーを 1 つのプロジェクトで作る
Supabase・Firebase　ログインと DB を借りる

チェックは両方に置く。画面のチェックはすり抜けられるので、保存するときはサーバーでも確かめる。

サーバーに置く理由

どれか 1 つでも「はい」なら、その処理やデータはサーバーに置く

任せられない
利用者の画面に任せず、正しい操作だけを許したいか例：誰のデータか、払ったか、承認・確定、保存するときのチェック
共有する
別の端末や他の人と、同じデータを使うか例：チームで使う一覧。開いているメニューのような、その画面だけの値はブラウザでよい
秘密と環境
見せてはいけない鍵を使うか。コマンドの起動など、ブラウザにはできないことをするかブラウザに届いたものは、利用者が全部見られる
閉じても続ける
画面を閉じたあとも動かすか例：決まった時刻の処理、長い AI の処理、外のサービスからの知らせの受け取り
入口が複数
画面のほかに、CLI や MCP からも同じ決まりを使うか決まりを画面の中に書くと、入口ごとに書き直しになる

ブラウザに置く理由

すぐ反応する
操作している間に、何度も回す処理か例：ドラッグ中の図形の計算、元に戻す・やり直す、入力中のチェック。通信を待たずに済む

重いだけでは、サーバーに置く理由にならない。ブラウザにも重い計算の仕組みがある（Web Workers、WebAssembly、WebGPU）。ただし端末の性能に左右され、タブを閉じれば止まる。WebGPU は、まだ使えないブラウザもある。

構成の決め方

自分で作る 借りる 使わない

  1. サーバーに置く理由が、1 つでもある？

    いいえ →

    型 A　ブラウザだけ

    ブラウザサーバーDB

    React と Vite。HTML・CSS・JavaScript だけでもよい

    はい ↓

  2. サーバーの処理を、自分で書く？

    書かない →
    ログインと DB があれば足りる

    ブラウザサーバーDB

    書く ↓

  3. サーバー側を Python などで書きたい？（すでにその言語の処理がある）

    はい →

    型 C　画面とサーバーを別々に作る

    ブラウザサーバーDB

この図は構成を選ぶ目安。唯一の正解ではない。型 B と型 D は人によって分かれ、組み合わせもできる（Next.js で作り、DB とログインだけ Supabase から借りる）。Python でデータを見せる画面を手早く作るだけなら、Streamlit・Gradio（型 E）もある。第8節で、使われている道具の規模を比べる。

最初は大きく分けるだけ

  1. 最初に決めるのは大きな境目だけ。表示はブラウザ、正式な保存と、皆で使うデータはサーバー
  2. 細かく分けるのは、別々の理由で変わることが見えてから。今要らない分け方は作らない（YAGNI：要るかもしれないだけのものは作らない、という考え方）
  3. 計算は画面の中に直接書かず、関数にしておく。あとで動く場所を移しやすい。ただし移すときは、通信・認証・失敗の扱いを書き足すことになる

役割の分け方（画面・業務・保存）と、動く場所の分け方（ブラウザ・サーバー）は、別の話

移せるか（移植性）

上ほど、別の置き場所へ移しやすい

  1. ファイルを配るだけ

    React と Vite で組み立てた画面

    同じファイルを別の所に置けば動く

  2. Node.js のサーバー、Docker のコンテナ

    Express、Hono、FastAPI、Next.js（Node.js か Docker で動かす）

    それが動く所なら、ほぼそのまま移せる。Hono は Node.js 以外（Cloudflare など）でも動く

  3. 公開先に合わせて変換するもの

    Next.js のアダプター

    Vercel など検証済みの公開先でないと、機能の対応が違うことがある

  4. 借りるバックエンド

    Supabase、Firebase

    データ、ログインの利用者、ファイルを全部移す。Supabase の DB は PostgreSQL なので移す道がある。Firestore は文書の形の DB で、表の DB へは作り直しが要る

移すときに困るのは、コードよりデータ。使い始める前に、丸ごと書き出せるかを確かめる

9. オブジェクト指向をやってきた人が、意識すること

React と Web では、状態の置き場所を自由に選べる。複雑にできる分、自分で決めないと散らばる

決めることオブジェクト指向React と Web
どこに置くかそのオブジェクトのフィールド部品の中、共通の親、ストア、サーバーの写し、URL……から選ぶ
誰が変えてよいかそのオブジェクトのメソッドだけ（private で守る）set を渡せば、どこからでも変えられる（ストアは特に）。入口を絞るのは自分
誰に伝えるか変えた本人が、画面に命じる（1 の命令型）通知の仕組みに載せないと、画面に伝わらない（2）

オブジェクト指向でも状態は管理している。メソッドの中に隠れていて、意識しなかっただけ

思いがちなこと

オブジェクト指向の感覚React では
画面はメソッドで書き換えるもの状態を変え、画面は状態から描く（1）
共有のオブジェクトを渡せば、画面も変わる通知がないと、React は描き直しが要ると分からない（2）
ふつうの変数を変えれば、画面も変わるuseState などで持つ（2）
配列は、そのまま書き換えればよい（items.push）新しい配列を作って set に渡す。状態の配列は読み取り専用として扱う
set した直後に、値は変わっている新しい値は、次の描画から（2）
共有の値は、全部 1 つのストアへどこからでも変えられる値は、グローバル変数と同じ問題を起こす。共有するのは必要なものだけ

AI と作るなら、なおさら

AI は、頼まれた機能を動かすために、その場で状態を足していく。置き場所の決まりがないと、同じ値があちこちに増える。

実際にあった例：microtaro が AI と作ったアプリで、「最新の版」を 27 か所がそれぞれ自分で計算していた

最初に伝える一文

オブジェクト指向でも、状態は共有できる。React で新しく意識するのは、状態の変更をどう画面へ伝え、その状態から画面をどう作るか、という仕組み。
