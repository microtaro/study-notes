Imperative UI in C++ sends a command for each change

// Start with an ordinary variable.
std::string message = "Hello";
screen.show(message);

// Change the greeting.
// Tell the screen to display it again.
message = "Goodbye";
screen.show(message);

Declarative UI in React updates the state

// React keeps the message in state.
const [message, setMessage] = useState("Hello");
return <Screen>{message}</Screen>;

// Change the greeting.
// Update the state.
setMessage("Goodbye");

The display update React handles (pseudocode)

screen.show(message);

What does each call update?

screen.show(message) → updates the screen

setMessage("Goodbye") → updates the state

Both examples need a display update. The C++ example puts it in application code, and the React example delegates it to React. C++ also supports declarative frameworks. The distinction is in how you describe the UI.

2. Keeping a view consistent with subscriptions and notifications

As the number of controls grows, more of them need to agree about the same state. How does a view learn that the state has changed?

One state keeps the controls in sync

While a message is being sent, disable the Send button and display “Sending…”.

Imperative

Update each control individually and restore each one when the request finishes. It is easy to forget one.

Disable the button and show “Sending…”.
→ Enable the button and hide “Sending…”.

Declarative

Describe both controls in terms of whether a send is in progress. Change that state when the request finishes.

Sending → Idle

The same reasoning applies to values you can calculate. If the Send button should be disabled when the input is empty, keep the text (message) in state. Derive the button’s availability from that text.

How a subscription leads to a notification

The view needs a way to learn about changes so it can display the latest state.

① Subscribe once when the view starts listening

“Tell me when message changes.”

② Notify whenever the value changes

ProgramState message

A notification says that something changed. The view’s description determines what to draw.

Why assigning to an ordinary variable does not update the screen

// An ordinary assignment does not schedule a render.
let message = "Hello";
message = "Goodbye";

// setMessage asks React to schedule a render.
const [message, setMessage] = useState("Hello");
setMessage("Goodbye");

This resembles the Observer pattern in object-oriented programming. With useState, the setter requests another render. Immediately after setMessage, the variable message still holds the value from this render. The new value is available on the next render.

4. Why manage state?

Placing message in the shared parent settled three questions at once.

Three decisions about a state value

The shared-parent example from section 3

  1. ① Where does it live? Keep one authoritative value. React calls this a single source of truth.
  2. ② Who can change it? Give changes a clear entry point. Here it is the setter passed to the input.
  3. ③ Who needs to know? Deliver the value to the components that use it, as in section 2.

Start with a shared parent. Context lets a parent supply a value to descendants without passing it through each intervening component. Section 5 considers an external store.

A stale synchronization result

An app microtaro built with AI kept the same synchronization result in four places. It lived in server memory, a file, browser storage, and the view’s cache. A stale result kept appearing. Correcting it took eleven revisions in one day.

The right home depends on whether a value belongs to one component, the whole screen, a copy of server data, or the URL. The diagram in section 7 gives examples for each kind of state.

5. Sharing state outside the component tree with Zustand

Components can subscribe directly to the values they use

Distant components can share a store outside their common tree. Zustand is one library for creating such a store.

Where should an unread count live?

The header contains an unread badge. The list contains a button that marks items as read.

Let the screen own the count, as in section 3

The header and list have to pass props they do not use. Updating state at the screen level normally renders the screen and its children again.

Put the count in a Zustand store

Each component selects what it needs. A count update triggers a render for subscribers whose selected value changed.

For a list fetched from the server, the lesson uses TanStack Query to manage the cached copy and refetch it. Putting it in the UI store would leave that refetching logic to the application (section 7).

In generated code, look for create(...) to create the store and a selector such as useUnreadStore((s) => s.count) to read the value a component needs.

6. What stateless HTTP means for a server

Each HTTP request makes sense on its own

The UI can hold state while the page is open. With HTTP, the server can interpret each request independently of previous requests. For example, a cookie can identify the session the application should load for a signed-in user.

Trace a request and its response

In this design each request can go to any server instance. The server checks the session identified by the cookie and reads the authoritative records from the database.

The application can restart a server or add instances and still handle the next request.

How UI state and stateless HTTP coexist

7. Dividing work between the browser and the server

Start in the browser. Add a server when a particular responsibility calls for one.

Revisit the three questions about state

Once data crosses the network, the three questions from section 4 have different answers.

DecisionWithin the UI (sections 2–5)Across the network
Where does it live?One shared owner.The server’s database holds the authoritative shared record. The browser has a copy.
Who can change it?Limit the entry points for updates.The server enforces allowed changes, including transitions such as approval or finalization.
Who needs to know?React propagates the state update.The view can refetch or the server can send an update. Options include polling, server-sent events, and WebSockets.

When data is shared across users, the network separates the authoritative record from the browser’s copy.

Each user and tab has its own in-memory UI state. A change made elsewhere appears after a refresh or notification. Checking the record’s version on save helps prevent one edit from overwriting another.

When does work belong on the server?

A “yes” to any of these questions gives you a reason to put that responsibility on the server.

Enforcing rules
Must the application independently verify that an operation is allowed?Examples include checking ownership, payment, approval, and inputs before saving.
Sharing
Do other users or devices need the same data?A team task list is shared. Which menu a user has opened can stay in the browser.
Secrets and capabilities
Does the operation need a secret key or a capability such as starting a system command?Users can inspect what is delivered to their browser.
Background work
Must the operation continue after the user closes the page?Examples include scheduled jobs, long AI tasks, and notifications from external services.
Multiple clients
Do a CLI or MCP client and a web UI need to follow the same rules?Rules embedded in a view have to be implemented again for each client.

When does work belong in the browser?

Immediate feedback
Does the operation run repeatedly during an interaction?Dragging a shape, undoing an edit, and validating input can all respond without a network round trip.

A browser can also handle intensive computation using Web Workers, WebAssembly, or WebGPU. Performance depends on the device, and closing the tab ends this work. Check WebGPU support on the browsers you target.

Start with broad boundaries

  1. Place display logic in the browser and the authoritative shared records on the server.
  2. Split responsibilities further when you see that they change for different reasons. The YAGNI principle suggests waiting until a separation is needed.
  3. Put calculations in functions that can be called independently of the UI. Moving one across a network later will also require communication, authentication, and error handling.

Which responsibility a function serves (display, business rules, storage) and where it runs (browser, server) are separate design decisions.

The options at the top have fewer hosting dependencies.

    Express, Hono, FastAPI, or Next.js with the appropriate runtime or container

    You can move the application to another host that supports its runtime. Hono also runs outside Node.js, for example on Cloudflare.

  3. A hosting-specific adapter

    Next.js adapters

  4. Managed backends

    Supabase and Firebase

Choosing among the options

  • Widely used tools are a reasonable starting point when you need examples and answers.
  • If you may change hosts, consider static files or containers and check whether the service can export all your data.
  • Give throughput more weight when you know you will have enough traffic for it to matter.

Decisions a class used to make explicit

DecisionObject-oriented exampleReact and the web
Where does it live?A field on the object.Choose a component, a shared parent, a store, cached server data, or the URL.
Who can change it?A private field can be changed through methods on the object.A component with access to a setter can call it. Explicit update functions can limit who changes shared state.
Who needs to know?In the imperative example in section 1, the code that changes the value also tells the view what to display.The update must reach React through a mechanism that triggers rendering (section 2).

An object already manages state. Its methods can hide the details from callers.

Familiar habits and their React equivalents

Familiar assumptionHow React handles it
Call a method to update the screen.Update state and describe the view that follows from it (section 1).
Passing a shared object updates the view.React needs a signal to render again when data changes (section 2).
Assigning to an ordinary variable updates the screen.useState is one way to retain a value and request a render (section 2).
Change the existing array in place (items.push).Treat an array held in state as read-only. Build a new array and pass it to the setter.
The variable changes immediately after calling the setter.The next render sees the updated value (section 2).
Put every shared value into a single store.Unrestricted writes create the same problems as global variables. Share only the values that need a common owner.

State ownership in AI-assisted development

When asked to implement a feature, an AI can add state where the feature needs it. Without an ownership rule, several pieces of code can end up tracking the same fact.

In one app microtaro built with AI, 27 different places independently calculated which version was the latest.

What to carry over from object-oriented design

Objects can already share state. The additional question in React is how a change reaches the UI and how the component describes the view that follows from that state.
